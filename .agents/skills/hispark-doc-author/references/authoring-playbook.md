# 编写工作手册

本手册是执行摘要。符合性判断仍以采用项目的 HiSpark 文档规范为准。

## 1. 先确定页面职责

| 用户当前要做什么 | `doc_type` | 页面应优化的目标 |
|---|---|---|
| 在受控路径中学习并第一次成功 | `tutorial` | 学习体验与可观察成果 |
| 完成现实任务或解决具体问题 | `how-to` | 行动、判断点与恢复 |
| 查询接口、参数、规格或确定事实 | `reference` | 准确、完整、可扫描 |
| 理解原因、关系、约束或取舍 | `explanation` | 概念模型与 know-how |

页面同时命中多个意图时，选择一个主要意图，把其他职责拆成独立页面并链接。产品导航层不等于文档类型层。

## 2. 建立事实包

写作前至少确认：

- 正式产品名、适用版本、Target、单板或硬件对象；
- 源码、公开头文件、配置、发布物或正式硬件资料位置；
- 已实际完成的验证及对应日志、产物或测试记录；
- 上游项目、匹配版本与稳定目标章节；
- Owner、页面状态和验证有效期。

无法确认的内容不能补写成产品事实。可以用“待验证”“未知”或“不适用”建立清晰边界。

## 3. 页面骨架

### 教程

依次覆盖：学习成果、适用版本、前置条件、预计用时、唯一受控路径、逐步预期结果、最终验证、清理和下一步。失败分支只保留高概率阻塞点，完整排障链接到实践指南。

### 实践指南

依次覆盖：目标、适用条件、前置状态、操作或决策步骤、主要分支、完成判据、回滚和相关资料。标题使用“如何……”或明确任务动词。

### 参考资料

以对象自身结构组织。API 至少考虑签名、参数方向、单位、范围、生命周期、返回值、错误码、并发/上下文/内存/权限约束、最小示例和源码来源。

### 解释说明

围绕一个“为什么”或关系问题，说明背景、概念模型、设计原因、约束、取舍、替代方案、边界及其对开发、调试或维护的影响。不得伪装成逐步操作，也不得重复完整 API 定义。

## 4. 专项约束

### `get-started/`

- 面向没有本产品经验的新用户，只保留一条默认 Happy Path；
- 第一次成功前不引入非必要架构、完整参数或可选分支；
- 每个前置条件可检查，每个主要步骤有动作、预期结果和恢复入口；
- 未经项目另行批准时，默认预算为一个入口页、一个快速入门页、不超过 7 个主要步骤、不超过 5 个前置条件、首次成功前 0 个可选分支；目标完成时间按规范建议控制在 30 分钟以内。

### Sample 实践指南

- 使用 `doc_type: how-to`，指向真实源码和配置入口；
- 明确产品、开发板、SDK 版本、Target、角色和互斥资源；
- “可构建”必须有构建证据，“目标板行为”必须有相应实板证据；
- 给出可机器或人工观察的成功判据，串口静默或缺少关键标记不能算通过。

### 上游与下游

- 不通过复制、近义改写、翻译粘贴或截图重建上游通用内容；
- 链接文字说明去哪里、完成什么、何时回到下游流程；
- 下游明确列出相对上游的增加、替换、限制和不适用项；
- 临时副本记录来源、上游版本、Owner、原因和复核日期。

### 图片

- 命令、代码、配置、日志、路径和参数使用文本表达；
- 图片必须有目的明确的替代文本，关键结论在正文或图注中有等价表达；
- 架构图、流程图和时序图保留可编辑源文件及导出映射；
- 截图裁到最小范围并清除凭据、内部地址、个人数据和设备唯一标识；
- 图片与页面共享 Owner、版本和生命周期。

## 5. 交付自检

- 一个页面只有一个主要 `doc_type`；
- 产品和版本边界明确，没有混入未声明能力；
- 命令可复制，执行环境、预期结果和失败恢复可见；
- 上游通用内容没有在下游形成第二事实源；
- 页面状态与实际证据相符；
- 所有链接和资源能从页面直接访问；
- 不可逆或高风险动作的警告出现在动作之前。
