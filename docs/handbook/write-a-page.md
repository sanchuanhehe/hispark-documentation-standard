## 先选择当前任务

| 读者需要 | 选择 | 下一步查阅 |
|---|---|---|
| 在引导下获得第一次成功 | 教程 `tutorial` | 本页教程模板；[快速入门预算](../part-2-authoring/08-specialized-content.md) |
| 完成具体任务或排障 | 实践指南 `how-to` | 本页实践指南模板；Sample 还查[专项要求](../part-2-authoring/08-specialized-content.md) |
| 查签名、参数或规格 | 参考资料 `reference` | 本页参考模板；[API 与硬件要求](../part-2-authoring/08-specialized-content.md) |
| 理解原因、关系或取舍 | 解释说明 `explanation` | 本页解释模板；[类型边界](../part-2-authoring/05-information-architecture.md) |

先按用户需求选类型，再按项目已有导航放置页面。完整目录映射见[第 5.2 节](../part-2-authoring/05-information-architecture.md)，不需要先调整仓库目录。

## 填一次页面事实

使用项目现有元数据机制填写以下信息；这里列字段语义，不规定文件格式。必填与条件适用规则见[第 6.1 节](../part-2-authoring/06-authoring.md)。

| 信息 | 填写内容 |
|---|---|
| 标题与类型 | 用户目标；四类 `doc_type` 中的一类 |
| 适用范围 | 正式产品、SDK/工具版本、Target、硬件对象、配置 |
| 责任与状态 | 可负责的 Owner；新稿从 `draft` 开始 |
| 来源 | 实际源码、配置、正式资料；适用时填写上游项目、版本和 URL |
| 验证 | 实际完成的等级、证据位置；`verified` 时填写验证日期 |

优先引用已有清单和记录。Owner、版本或验证结论不明时先标记缺口，由对应负责人确认。

## 教程模板

1. **你将完成什么**：一个可观察的学习成果。
2. **适用版本与开发板**：预先选择的一组受支持组合。
3. **前置条件**：逐项给出检查方法。
4. **预计用时**：带单位的数值目标、计时边界和用户测试依据；Get Started 的预算及例外按第 8.1 节处理，尚未测试不等于免填数值目标。
5. **分步骤操作**：每步说明动作，关键步骤后紧跟预期结果；保留高概率阻塞点的恢复入口。
6. **最终验证**：用明确判据确认学习成果。
7. **清理与下一步**：恢复环境，链接到实践指南或解释说明。

第一次成功前不放可选方案、完整参数表或长篇架构背景。它们在成功后的链接中提供。

多平台入口先区分入口决策、叶子教程和平台展示变体；纯导航页不套教程模板。逐叶预算见[第 8.1 节](../part-2-authoring/08-specialized-content.md)，八阶段验证见[第 9.4 节](../part-3-quality/09-validation-and-testing.md)，规范采用记录见[第 12.4 节](../part-4-governance/12-governance-and-maintenance.md)。

## 实践指南模板

1. **目标**：用户要完成的具体任务。
2. **适用条件与前置状态**：产品、版本、配置、资源及检查方法。
3. **操作或决策步骤**：执行目录、权限、命令、判断点和预期结果。
4. **主要分支与限制**：现实场景中的选择和不适用情况。
5. **验证完成**：可观察标记、结果或产物。
6. **回滚或恢复**：失败时如何继续；危险动作的警告放到动作之前。
7. **相关资料**：链接到接口参考和设计解释。

Sample 页面在此基础上连接真实源码入口、配置选项、稳定 `sample_id`、Owner 和测试记录。代码、文档、测试属于同一个维护单元，详见[Sample 维护契约](#sample-maintenance-contract)。

> **前置条件：** 使用 `<product>` 的 `<sdk-version>`，上游工具固定为 `<tool-version>`。先打开“上游工具对应版本的安装指南”并完成该版本的安装验证，再返回本页。发布页面时，将引号内文字替换为目标章节链接。

## 参考资料模板

依次填写：对象与头文件/正式资料；适用版本及限制；签名或规格；参数方向、单位、范围、默认值及生命周期；返回值与错误条件；并发、中断、内存与权限约束；最小示例；事实源及相关指南。只填写对该对象适用的项目，不虚构参数或限制。

API 从当前发布头文件或生成源核对，硬件数据从正式资料核对。生成源、版本及人工补充边界保持可追溯。

## 解释说明模板

依次回答：要解释什么问题；问题出现的背景；概念和组成关系；设计原因及约束；替代方案与取舍；对开发、调试或维护的影响；相关操作和参考入口。

将“资料证明的事实”“已作出的设计决策”“推论”“建议”分开。不要用完整 API 定义或长串命令代替原因分析。

## 提交前怎么检查

使用[第 14.1 节的文档变更清单](../part-4-governance/14-conformance-checklist.md)，提交实际来源、验证结果和未验证边界。根据[Reviewer 矩阵](../part-3-quality/10-review-and-merge.md)请求对应角色评审。

遇到链接、格式、命名、图片尺寸等确定性问题，优先使用项目已有检查；产品事实、步骤是否好用以及证据是否支持声明仍需人工判断。模板填完不等于已获得批准。
