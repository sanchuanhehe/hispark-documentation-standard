本页说明怎样开始写，并提供模板，不增加正文之外的要求。完整要求见第 5—8 章；第一次使用先读[基础规范](../part-1-foundations/04-core-principles.md)。模板中的占位符要换成项目的真实信息。不知道的内容先标为待确认，不能写成已经验证的事实。

## 先选择当前任务

| 读者需要 | 选择 | 下一步查阅 |
|---|---|---|
| 在引导下获得第一次成功 | 教程 `tutorial` | 本页教程模板；[快速入门预算](../part-2-authoring/08-specialized-content.md) |
| 完成具体任务或排障 | 实践指南 `how-to` | 本页实践指南模板；Sample 还查[专项要求](../part-2-authoring/08-specialized-content.md) |
| 查签名、参数或规格 | 参考资料 `reference` | 本页参考模板；[API 与硬件要求](../part-2-authoring/08-specialized-content.md) |
| 理解原因、关系或取舍 | 解释说明 `explanation` | 本页解释模板；[类型边界](../part-2-authoring/05-information-architecture.md) |

先想清楚用户要做什么，选好文档类型，再把页面放进项目已有导航。各目录放什么内容，见[第 5.2 节](../part-2-authoring/05-information-architecture.md)，不用先调整仓库目录。

## 填一次页面事实

按项目现有的元数据方式填写以下信息。这里说明填什么，不规定保存格式。哪些必填、哪些只在特定条件下填写，见[第 6.1 节](../part-2-authoring/06-authoring.md)。

| 信息 | 填写内容 |
|---|---|
| 标题与类型 | 用户目标；四类 `doc_type` 中的一类 |
| 适用范围 | 正式产品、SDK/工具版本、Target、硬件对象、配置 |
| 责任与状态 | 可负责的 Owner；新稿从 `draft` 开始 |
| 来源 | 实际源码、配置、正式资料；适用时填写上游项目、版本和 URL |
| 验证 | 实际完成的等级、证据位置；`verified` 时填写验证日期 |

已有清单和记录的，优先引用。Owner、版本或验证结论不清楚，就先标出来，请相应负责人确认。

## 教程模板

1. **你将完成什么**：用户学完能做成什么，怎样看到结果。
2. **适用版本与开发板**：作者预先选好的一组受支持组合。
3. **前置条件**：逐项说明怎样检查准备是否完成。
4. **预计用时**：写出带单位的数值目标，说明哪些时间算在内，以及用户测试依据。Get Started 的预算及例外按第 8.1 节处理；还没测试，不等于可以不填目标。
5. **分步骤操作**：每步说明做什么，关键步骤后说明会看到什么；常见的阻塞点附上恢复入口。
6. **最终验证**：说明怎样判断学习成果已经达到。
7. **清理与下一步**：恢复环境，链接到实践指南或解释说明。

先让用户做成这件事，再提供可选方案、完整参数表和架构背景的链接，不把这些内容放在首次成功之前。

支持多个平台时，先分清用户需要做哪些入口选择、选完后执行哪篇叶子教程、哪些只是平台展示不同。只提供导航的页面不用套教程模板。每个叶子的预算见[第 8.1 节](../part-2-authoring/08-specialized-content.md)，八阶段验证见[第 9.4 节](../part-3-quality/09-validation-and-testing.md)，规范采用记录见[第 12.4 节](../part-4-governance/12-governance-and-maintenance.md)。

## 实践指南模板

1. **目标**：用户要完成的具体任务。
2. **适用条件与前置状态**：产品、版本、配置、资源及检查方法。
3. **操作或决策步骤**：执行目录、权限、命令、判断点和预期结果。
4. **主要分支与限制**：现实场景中的选择和不适用情况。
5. **验证完成**：可观察标记、结果或产物。
6. **回滚或恢复**：失败时如何继续；危险动作的警告放到动作之前。
7. **相关资料**：链接到接口参考和设计解释。

Sample 页面还要关联真实源码入口、配置选项、稳定 `sample_id`、Owner 和测试记录。代码、文档和测试一起维护，详见[Sample 维护契约](#sample-maintenance-contract)。

### 示例：引用上游安装指南

下面只示范内容组织；不声明任何具体产品能力。

> **前置条件：** 使用 `<product>` 的 `<sdk-version>`，上游工具固定为 `<tool-version>`。先打开“上游工具对应版本的安装指南”并完成该版本的安装验证，再返回本页。发布页面时，将引号内文字替换为目标章节链接。
>
> **本产品差异：** 只写本产品实际增加的配置、Target 选择、限制和不适用项；没有差异时直接进入验证。
>
> **验证完成：** 填入本产品实际执行的步骤、成功判据和证据链接。没有实板证据，就写清这部分尚未验证，保留待验证状态。

这样写能让上游继续维护安装流程，下游负责产品适配和验证。把上游全文翻译后粘贴进来，仍会产生独立维护的副本；例外条件见[第 7 章](../part-2-authoring/07-upstream-downstream.md)。

## 参考资料模板

依次填写：对象与头文件/正式资料；适用版本及限制；签名或规格；参数方向、单位、范围、默认值及生命周期；返回值与错误条件；并发、中断、内存与权限约束；最小示例；事实源及相关指南。只填写对该对象适用的项目，不虚构参数或限制。

API 对照当前发布的头文件或生成源核对，硬件数据对照正式资料核对。保留生成源和版本信息，并说明哪些内容由人工补充，方便后续查证。

## 解释说明模板

依次回答：要解释什么问题；问题出现的背景；概念和组成关系；设计原因及约束；替代方案与取舍；对开发、调试或维护的影响；相关操作和参考入口。

将“资料证明的事实”“已作出的设计决策”“推论”“建议”分开。不要用完整 API 定义或长串命令代替原因分析。

## 提交前怎么检查

按[第 14.1 节的文档变更清单](../part-4-governance/14-conformance-checklist.md)检查，提交实际来源和验证结果，说明还有哪些部分没验证。再按[Reviewer 矩阵](../part-3-quality/10-review-and-merge.md)请相应角色评审。

链接、格式、命名、图片尺寸等可以按固定规则检查的内容，优先用项目已有工具。产品事实是否正确、步骤是否好用、证据是否支持文档说法，仍需人工判断。填完模板不等于已经通过评审。
