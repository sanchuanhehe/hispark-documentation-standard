## 8.1 `get-started/` 规模与认知负担

`get-started/` MUST 保持小、可控，并以没有本产品经验的新用户为目标读者。其职责是让用户沿唯一默认路径获得第一次成功，不是收纳完整环境手册、所有产品组合或高级配置。

1. `get-started/` MUST 保持唯一首次成功目标和完成判据，而不是限制为一个页面。入口决策 MUST 使用用户可理解的互斥问题完成分流；所选叶子教程 MUST 保持单路径。CLI 与 VS Code MAY 作为一次交互方式决策。Windows 与 Linux 若目标、主要动作和完成判据相同、仅命令或环境不同，MUST 计为同一平台维度的展示变体，不作为多个独立目标。
2. 第一次成功之前 MUST NOT 要求用户理解非必要架构、内部模块、全部参数或历史背景；这些内容 MUST 链接到实践指南、参考资料或解释说明。
3. 教程 MUST 预先选择并明确一组受支持的产品、单板、Target、工具链和配置，MUST NOT 在关键步骤中让新用户自行猜测。
4. 每个前置条件 MUST 可检查；每个主要步骤 MUST 给出动作、预期结果和失败后的恢复入口。
5. 首次出现的必要术语 MUST 立即用用户语言解释。未解释的缩写、内部代号、隐含目录和隐含环境变量 MUST NOT 成为完成路径的前提。
6. 首次成功不可缺少的最小环境检查和准备 MUST 在所选教程中完成，或由教程直接进入版本匹配的准备步骤并明确返回位置。完整安装百科、企业策略、可选工具和性能优化 MUST 放在实践指南、参考资料或正式上游，MUST NOT 成为首次成功前置。`get-started/` 只保留必要的最小调用和下游差异；上游复用遵循[第 7 章](07-upstream-downstream.md)。
7. 项目 MUST 定义并在 CI 中逐叶检查页面数、主要步骤数、前置条件数、独立决策数、首次成功前可选分支数和目标完成时间的数值预算。公共入口及必要的外部准备 MUST 纳入所选叶子的用户路径核算，MUST NOT 通过拆页或外链隐藏负担。
8. 同一独立决策的重复联动选择 MUST 只计一次，但所有出现位置的标签、顺序和语义 MUST 一致，选择状态 MUST 保持联动。不能保持一致或引入新选择语义时，MUST 作为独立决策核算。平台展示相同 MUST NOT 代替逐变体验证，验证矩阵见[第 9.4 节](../part-3-quality/09-validation-and-testing.md)。

首次成功前的可选分支预算 MUST 为零；必要的互斥入口决策与成功后优化 MUST 分开记录。其余上限 MUST 由项目基于目标用户测试和文档架构评审批准，MUST NOT 以固定页数、步骤数或前置条件数代替认知负担判断。没有获批的数值预算 MUST 判为缺口，MUST NOT 默认为不限量或合格。已有更严格项目预算 MUST 保持有效，改变上限 MUST 重新评审，MUST NOT 仅为消除 CI 发现而调高预算。

目标完成时间 MUST 为带单位的正数，并记录计时起点、必要准备/下载是否计入及用户测试条件；MUST NOT 以“暂不承诺完成时间”替代。目标完成时间 SHOULD 不超过 30 分钟。超出预算或偏离上述时间要求的例外 MUST 提供原因、Owner、用户测试证据和复核日期，经文档架构评审，并按[第 12.2 节](../part-4-governance/12-governance-and-maintenance.md)限期批准。

:::{admonition} 背景与解决思路：快速入门不断膨胀（非规范性）
:class: note

**问题背景。** 新用户尚未形成产品心智模型时，单板、Target、工具链、配置和可选方案看起来同等重要。作者为了覆盖更多场景而持续增加前置说明和分支，会让用户在第一次成功前反复猜测，走错路径后也难以判断从哪里恢复。

**解决机制。** 预先选择一组受支持组合，把前置条件变成可检查项，并在主要步骤后给出可观察结果；页面数、步骤数、分支数和目标用时预算则用于防止高级内容回流到入口页面。

**预期效果。** 新用户可以沿单一路径尽早获得第一次成功，复杂场景仍能通过链接按需进入。逐叶预算暴露真实路径上的负担，而不会把多平台展示误算为多个目标，也不会让拆页后的准备成本从检查中消失。
:::

## 8.2 Sample 实践指南

1. `samples/` 的案例页面 MUST 使用 `doc_type: how-to`，并 MUST 指向仓库内真实源码路径。
2. 页面 MUST 给出启用示例所需的 Kconfig 选项、角色和互斥资源。
3. 页面 MUST 标明支持的芯片、开发板、SDK 版本和 Target。
4. 代码片段 SHOULD 从可构建源码提取或由测试验证，MUST NOT 长期维护无来源副本。
5. 示例声称“可运行”时，至少 MUST 有可复现构建证据；声称目标板行为时，MUST 有相应 HIL 或人工实板验证证据。
6. 暂不可运行、占位或仅设计中的示例 MUST 标明状态，并 MUST NOT 出现在默认推荐路径中。
7. 示例 MUST 给出成功判据，例如串口标记、返回码、网络行为或产物哈希。
8. 串口静默或缺少关键标记 MUST NOT 被判定为通过。

本节规定 Sample 页面如何编写；其测试覆盖和分层执行要求见[第 9.2—9.3 节](#sample-test-coverage)，Owner、清单和生命周期要求见[第 12.3 节](#sample-maintenance-contract)。

## 8.3 API 参考

- 公共 API 文档 MUST 与发布头文件一致。
- 新增、修改或删除 API 时，对应参考资料 MUST 在同一变更中更新。
- API 页面 MUST 明确不支持或受限能力，例如角色、协议、上下文和线程安全限制。
- 示例调用 MUST 使用当前签名、枚举和错误码。
- 自动生成 API 文档 SHOULD 将源码符号作为单一事实源。

## 8.4 硬件参考

- 硬件规格 MUST 标明资料版本和适用芯片/单板版本。
- 电压、频率、温度、单位和容差 MUST 使用统一单位并与正式资料一致。
- 器件选型、射频和产测内容 MUST 明确测试条件与责任边界。
- 软件仓库中的摘要 MUST 链接到正式硬件资料，MUST NOT 成为未经维护的第二份规格源。
