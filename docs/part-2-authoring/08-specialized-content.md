## 8.1 `get-started/` 规模与认知负担

`get-started/` 必须（MUST）面向第一次使用本产品的用户，保持内容简短、范围可控。它带领用户沿唯一默认路径先做成一件事，不用来收纳完整环境手册、所有产品组合或高级配置。

1. `get-started/` 必须（MUST）明确唯一的首次成功目标和完成判据，可以分成多个页面。入口决策必须（MUST）用用户能理解、选项互斥的问题帮助用户选路；选定的叶子教程必须（MUST）只提供一条操作路径。CLI 与 VS Code 可以（MAY）算作一次交互方式选择。Windows 与 Linux 如果目标、主要动作和完成判据相同，只是命令或环境不同，必须（MUST）算作同一平台维度下的展示变体，不另算多个目标。
2. 第一次成功之前不得（MUST NOT）要求用户理解非必要架构、内部模块、全部参数或历史背景；这些内容必须（MUST）链接到实践指南、参考资料或解释说明。
3. 教程必须（MUST）预先选择并明确一组受支持的产品、单板、Target、工具链和配置，不得（MUST NOT）在关键步骤中让新用户自行猜测。
4. 每个前置条件必须（MUST）可检查；每个主要步骤必须（MUST）给出动作、预期结果和失败后的恢复入口。
5. 必要术语第一次出现时，必须（MUST）立即用用户能理解的话解释。完成操作不得（MUST NOT）依赖未解释的缩写、内部代号，或未写明的目录和环境变量。
6. 首次成功所必需的最小环境检查和准备，必须（MUST）在所选教程内完成，或直接链接到匹配版本的准备步骤，并说明做完后回到哪里。完整安装百科、企业策略、可选工具和性能优化必须（MUST）放在实践指南、参考资料或正式上游，不得（MUST NOT）作为首次成功的前置条件。`get-started/` 只保留必要的最小调用和下游差异；上游复用遵循[第 7 章](07-upstream-downstream.md)。
7. 项目必须（MUST）为每个叶子教程设定数值预算，并在 CI 中逐个检查：页面数、主要步骤数、前置条件数、独立决策数、首次成功前可选分支数和目标完成时间。公共入口及必要的外部准备必须（MUST）一起计入用户所选路径，不得（MUST NOT）因拆成多页或改为外链就不算这部分负担。
8. 同一问题在多个位置重复出现，且选择状态联动时，必须（MUST）只计一次决策。但各处的标签、顺序和含义必须（MUST）一致，选择状态必须（MUST）保持联动。如果不一致，或实际提出了新的选择问题，必须（MUST）另计一次独立决策。平台展示相同，不得（MUST NOT）代替对各变体分别验证，验证矩阵见[第 9.4 节](../part-3-quality/09-validation-and-testing.md)。

首次成功前的可选分支预算必须（MUST）为零；必要的互斥入口选择和成功后优化必须（MUST）分开记录。其余上限必须（MUST）由项目根据目标用户测试和文档架构评审批准，不得（MUST NOT）只凭固定的页数、步骤数或前置条件数判断用户是否容易上手。

没有获批的数值预算，必须（MUST）记为缺口，不得（MUST NOT）默认不限量或已经合格。项目已有更严格的预算，必须（MUST）继续执行；修改上限必须（MUST）重新评审，不得（MUST NOT）只为消除 CI 报出的问题而调高预算。

目标完成时间必须（MUST）写成带单位的正数，并记录从哪里开始计时、是否计入必要准备和下载，以及用户测试条件；不得（MUST NOT）用“暂不承诺完成时间”代替。目标完成时间应当（SHOULD）不超过 30 分钟。

超出预算或偏离上述时间要求时，例外必须（MUST）提供原因、Owner、用户测试证据和复核日期，经文档架构评审，并按[第 12.2 节](../part-4-governance/12-governance-and-maintenance.md)限期批准。

:::{admonition} 背景与解决思路：快速入门不断膨胀（非规范性）
:class: note

**问题背景。** 第一次接触产品的用户，往往不知道该选哪块板、哪个 Target、哪套工具链和配置。如果快速入门把所有选项都摆出来，用户还没做成一件事，就要先猜很多答案。选错后，也不知道该从哪一步重新开始。

**解决机制。** 作者先选好一组受支持的组合，写清准备条件怎么检查、每个主要步骤做完后会看到什么。再用页面数、步骤数、分支数和目标用时的预算，检查有没有把高级内容又塞回快速入门。

**预期效果。** 用户能先顺着一条路径做成一件事，需要复杂用法时再看相关链接。按每个叶子教程计算预算，能看出用户实际要做多少准备、走多少步；不会把不同平台的展示算成多个目标，也不会漏掉放在其他页面里的准备工作。
:::

## 8.2 Sample 实践指南

1. `samples/` 的案例页面必须（MUST）使用 `doc_type: how-to`，并必须（MUST）指向仓库内真实源码路径。
2. 页面必须（MUST）给出启用示例所需的 Kconfig 选项、角色和互斥资源。
3. 页面必须（MUST）标明支持的芯片、开发板、SDK 版本和 Target。
4. 代码片段应当（SHOULD）从可构建源码提取或由测试验证，不得（MUST NOT）长期维护无来源副本。
5. 示例声称“可运行”时，至少必须（MUST）有可复现构建证据；声称目标板行为时，必须（MUST）有相应 HIL 或人工实板验证证据。
6. 暂不可运行、占位或仅设计中的示例必须（MUST）标明状态，并不得（MUST NOT）出现在默认推荐路径中。
7. 示例必须（MUST）给出成功判据，例如串口标记、返回码、网络行为或产物哈希。
8. 串口静默或缺少关键标记不得（MUST NOT）被判定为通过。

本节规定 Sample 页面如何编写；其测试覆盖和分层执行要求见[第 9.2—9.3 节](#sample-test-coverage)，Owner、清单和生命周期要求见[第 12.3 节](#sample-maintenance-contract)。

## 8.3 API 参考

- 公共 API 文档必须（MUST）与发布头文件一致。
- 新增、修改或删除 API 时，对应参考资料必须（MUST）在同一变更中更新。
- API 页面必须（MUST）明确不支持或受限能力，例如角色、协议、上下文和线程安全限制。
- 示例调用必须（MUST）使用当前签名、枚举和错误码。
- 自动生成 API 文档应当（SHOULD）将源码符号作为单一事实源。

## 8.4 硬件参考

- 硬件规格必须（MUST）标明资料版本和适用芯片/单板版本。
- 电压、频率、温度、单位和容差必须（MUST）使用统一单位并与正式资料一致。
- 器件选型、射频和产测内容必须（MUST）明确测试条件与责任边界。
- 软件仓库中的摘要必须（MUST）链接到正式硬件资料，不得（MUST NOT）成为未经维护的第二份规格源。
