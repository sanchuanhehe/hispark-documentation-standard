## 6.1 必需元数据

新建或实质性重写的内容页必须（MUST）通过项目统一的结构化元数据机制提供下列字段。元数据的物理表示方式由采用项目决定，但字段语义、取值约束和校验结果必须（MUST）保持一致。

字段规则：

| 字段 | 要求 |
|---|---|
| `title` | 必须（MUST）面向用户问题，避免仅使用内部模块代号 |
| `doc_type` | 必须（MUST）为 `tutorial`、`how-to`、`reference` 或 `explanation` |
| `product` | 必须（MUST）使用正式产品名；跨产品页面必须（MUST）明列全部适用产品 |
| `applies_to` | 与软件或硬件版本相关时必须（MUST）给出 SDK、Target、单板或工具版本 |
| `status` | 必须（MUST）为 `draft`、`reviewed`、`verified`、`deprecated` 之一 |
| `owner` | 必须（MUST）指向可负责评审与过期处理的团队或角色 |
| `last_verified` | `verified` 页面必须（MUST）使用 ISO 8601 日期 |
| `verification_level` | 必须（MUST）为 `static`、`build`、`smoke`、`hil` 或 `not-applicable`；表示声明的证据等级，不表示场景执行状态 |
| `source_refs` | 代码、配置、接口或样例相关页面必须（MUST）给出可审查的源码路径 |
| `upstream_refs` | 依赖上游说明时必须（MUST）给出上游项目、适用版本和稳定 URL；不依赖时可以（MAY）省略 |

`status: verified` 不得（MUST NOT）在缺少相应证据时使用。对于硬件运行结果，`verification_level: hil` 通常是必需（REQUIRED）的。

场景执行状态必须（MUST）单独记录为 `passed`、`failed`、`blocked`、`not_run` 或 `not_applicable`，含义见[第 9.4 节](../part-3-quality/09-validation-and-testing.md)。`not_run`、`blocked`、`failed` 不得（MUST NOT）写入验证等级；单个场景通过不得（MUST NOT）推导其他场景或更高等级通过。已有等价状态拼写可以（MAY）通过显式映射兼容，不得（MUST NOT）混淆未运行、阻塞和失败。

纯导航页必须（MUST）具有标题、Owner、页面角色、适用范围和生命周期状态；项目可以（MAY）用 `doc_type: navigation` 或独立字段表达导航角色，不得（MUST NOT）将其计作四类内容之一。导航页只声明自身导航、链接和范围的检查证据，不得（MUST NOT）继承所链接教程的验证状态。出现实质教学或操作流程时，必须（MUST）按相应内容类型拆分或重新分类。

## 6.2 版本与生命周期

### 6.2.1 版本适用性

1. 页面必须（MUST）明确适用于发布版本、维护分支还是 `master`。
2. 文档不得（MUST NOT）使用无日期、无链接的“最新版本”作为唯一版本说明。
3. 版本选择器、页面元数据、下载地址和源码分支应当（SHOULD）保持一致。
4. 发布文档必须（MUST）链接到可验证的 SDK 获取入口和发布说明。

### 6.2.2 状态

| 状态 | 含义 | 发布要求 |
|---|---|---|
| `draft` | 内容尚未完成或尚未评审 | 不得（MUST NOT）进入默认稳定导航 |
| `reviewed` | 已完成内容与技术评审 | 可以（MAY）发布，但必须（MUST）标明尚未完成运行验证的部分 |
| `verified` | 已按声明的验证级别通过 | 可以（MAY）进入推荐路径 |
| `deprecated` | 不再推荐，但为兼容保留 | 必须（MUST）显示替代页面、停止版本和迁移路径 |

页面只有在完成[第 10.2 节](#review-requirements)适用的全部 Review，且批准仍对应当前提交时，才可以（MAY）标记为 `reviewed`。`verified` 在此基础上还必须（MUST）满足声明的验证级别和[第 10.4 节](#definition-of-done)完成定义。

无人负责、长期未验证或已失去适用版本的页面必须（MUST）进入复核；无法恢复可信度时应当（SHOULD）下线或归档。

## 6.3 页面结构模板

### 6.3.1 教程模板

教程应当（SHOULD）按[写作入口中的教程模板](../handbook/write-a-page.md)组织：成果、适用范围、前置条件、用时、操作、预期结果、验证、清理和下一步。教程中的每个关键动作必须（MUST）提供可观察结果。失败分支应当（SHOULD）只覆盖高概率阻塞点，完整排障必须（MUST）链接到实践指南。

### 6.3.2 实践指南模板

实践指南应当（SHOULD）按[写作入口中的实践指南模板](../handbook/write-a-page.md)组织，覆盖目标、条件、前置状态、动作与判断、主要分支、验证、恢复和相关资料。

涉及擦除 Flash、修改 eFuse、覆盖配置、密钥操作或不可逆行为时，页面必须（MUST）在动作之前给出明确警告和恢复边界。

### 6.3.3 参考资料模板

API 参考应当（SHOULD）按[写作入口中的参考资料模板](../handbook/write-a-page.md)组织，覆盖头文件、适用性、签名、参数、返回值、执行约束、最小示例和来源。自动生成内容可以（MAY）使用，但生成源、版本和人工补充边界必须（MUST）明确。

### 6.3.4 解释说明模板

解释说明应当（SHOULD）按[写作入口中的解释说明模板](../handbook/write-a-page.md)组织，覆盖主题、背景、概念关系、设计约束、取舍、实际影响和相关入口。

## 6.4 标题、命名与链接

### 6.4.1 标题用语

- 教程标题应当（SHOULD）描述可完成的学习成果。
- 实践指南标题应当（SHOULD）采用“如何……”或明确的任务动词。
- 参考资料标题应当（SHOULD）使用对象名称加“API 参考”“参数参考”“硬件参考”。
- 解释说明标题应当（SHOULD）使用主题、关系、机制或设计问题。
- 标题不得（MUST NOT）仅使用“介绍”“说明”“其他”“杂项”“相关内容”。

### 6.4.2 命名与链接

1. 新目录和页面标识必须（MUST）使用小写 ASCII `kebab-case`，例如 `power-management`、`flash-and-run`；物理文件扩展名由采用项目决定。
2. 已发布的中文路径可以（MAY）为 URL 兼容保留；新文件名不得（MUST NOT）使用空格、含义不明的数字串或临时后缀。
3. 图片文件名应当（SHOULD）描述内容和状态，例如 `flash-success.png`。
4. 内部文档引用必须（MUST）使用可点击的相对链接，不得（MUST NOT）只写文件名或文档名。
5. 链接目标、标题锚点和路径大小写必须（MUST）在 Linux 构建环境中验证。
6. 外链应当（SHOULD）指向官方、稳定、版本匹配的来源。
7. 页面删除、移动或重命名必须（MUST）联合检查文件、导航、站内引用和旧 URL；必须（MUST）提供重定向、说明替代入口的保留页（tombstone）或可查的迁移映射，并验证旧入口的处置。仅删除源文件不得（MUST NOT）视为迁移完成。

## 6.5 写作与格式

1. 文档必须（MUST）使用简体中文和中文标点；代码、命令、路径、符号和正式产品名保持原样。
2. 句子应当（SHOULD）简洁，主动语态优先；一步应当（SHOULD）只表达一个主要动作。
3. 命令必须（MUST）放入带语言标记的代码块，并应当（SHOULD）可直接复制。
4. 命令前必须（MUST）说明执行目录、权限和环境；命令后应当（SHOULD）给出关键预期输出。
5. 占位符必须（MUST）使用可识别形式，例如 `<sdk-root>`，并必须（MUST）在首次出现时解释。
6. 表格必须（MUST）有明确表头；复杂流程应当（SHOULD）优先使用列表、分段或图，而不是超宽表格。
7. 项目不应（SHOULD NOT）直接嵌入绕过内容模型和主题系统的表现层标记；可由项目批准的结构化内容组件表达时应当（SHOULD）使用该组件。
8. 警告必须（MUST）放在危险动作之前，必须（MUST）说明风险、影响对象和恢复方式。

## 6.6 图片与可视化内容

文档应当（SHOULD）优先使用可检索、可复制、可访问且易于版本维护的文字、代码和结构化数据。图片数量本身不得（MUST NOT）作为质量指标；作者和 Reviewer 必须（MUST）判断每张图片是否传递了文字难以等效表达的必要信息。

1. 命令、代码、配置、日志、错误信息、路径和参数表必须（MUST）使用文本、代码块或表格表达，不得（MUST NOT）只以截图承载。
2. 图片应当（SHOULD）用于界面位置、硬件接线、物理状态、波形、空间关系或其他视觉关系确实影响理解和操作的场景。
3. 图片中的关键结论、操作目标和完成判据必须（MUST）同时出现在正文、图注或有效替代文本中，不得（MUST NOT）要求用户仅凭观察图片推断。
4. 架构图、流程图和时序图应当（SHOULD）使用可编辑、可版本管理的文本化或结构化图源。导出图片时，源文件必须（MUST）与导出产物建立明确映射并一同维护。
5. 线条图和图标应当（SHOULD）使用 SVG；需要保留像素细节的截图或照片可以（MAY）使用 PNG、JPEG 或项目批准的格式。动画和视频不得（MUST NOT）成为关键步骤或结论的唯一载体。
6. 截图必须（MUST）裁剪到完成任务所需的最小区域，应当（SHOULD）标注适用产品、软件版本、操作系统或界面状态。装饰性边框、无关桌面区域和重复截图不应（SHOULD NOT）保留。
7. 每张有信息意义的图片必须（MUST）提供描述其目的和关键内容的替代文本；装饰性图片可以（MAY）使用空替代文本，并应当（SHOULD）能在不影响理解的情况下删除。
8. 图片中的账号、密钥、令牌、内部地址、个人数据、设备唯一标识和其他受限信息必须（MUST）在提交前不可逆地移除或脱敏，不得（MUST NOT）只使用可撤销的标注层遮盖。
9. 图片包含文字时，正文必须（MUST）提供等价信息。面向多语言发布的页面应当（SHOULD）避免把大段可翻译文字固化在图片中；确有必要时必须（MUST）保留可编辑源文件和对应语言版本。
10. 同一视觉资产应当（SHOULD）由单一来源复用，不得（MUST NOT）在多个下游页面复制后独立维护。修改共享图片时必须（MUST） Review 所有引用页面的适用性。
11. 项目应当（SHOULD）规定图片格式、最大文件大小、像素尺寸和压缩策略。优化不得（MUST NOT）造成文字、引脚、波形或界面状态无法辨认。
12. 图片必须（MUST）与页面具有相同的 Owner、版本和生命周期边界。产品界面、接线、版本或事实变化后，过期图片必须（MUST）更新、降级为待复核或删除。

:::{admonition} 背景与解决思路：图片难以随产品演进（非规范性）
:class: note

**问题背景。** 截图制作快捷，却会把界面版本、语言、主题、账号状态和操作结果固化在像素中。界面变化后，文本差异检查通常无法发现图片已过时；图中文字也无法被可靠地搜索、复制或翻译，还可能无意带入账号、路径和受限信息。

**解决机制。** 让命令和技术事实保留为文本，让图片主要承担依赖视觉关系的内容，并补充等价文字、Owner 和适用版本；对架构图、流程图等适合结构化维护的图形保留可编辑图源，可以把视觉资产纳入可追踪的变更链。

**预期效果。** Reviewer 能判断图片是否必要、是否仍匹配当前页面；产品变化时，团队也能定位受影响资产，而不是依靠人工记忆寻找陈旧截图。
:::
