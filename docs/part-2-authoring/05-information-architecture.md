## 5.1 Diátaxis 标准文档类型

### 5.1.1 教程（Tutorial）

标准中文名：**教程**  
元数据值：`tutorial`

教程是面向学习的、由作者引导的完整实践体验。其目标是帮助学习者获得技能和信心，而不只是完成一次任务。

教程：

- MUST 给出可达到、可观察的学习成果；
- MUST 提供一条受控的成功路径；
- MUST 说明前置条件，并尽量减少选择与分支；
- MUST 在关键步骤后给出预期结果；
- MUST 经过端到端复现；
- SHOULD 让学习者尽早看到有意义的结果；
- SHOULD 将扩展原理和完整参数链接到解释说明或参考资料；
- MUST NOT 退化为 API 罗列、选项大全或开放式任务集合。

典型标题：

- “构建并运行第一个示例应用”
- “使用 SLE 完成首次设备连接”

### 5.1.2 实践指南（How-to guide）

标准中文名：**实践指南**  
导航栏目 MAY 使用“开发指南”  
元数据值：`how-to`

实践指南面向已有基本能力的用户，帮助其在现实约束下完成具体任务或解决具体问题。

实践指南：

- MUST 以用户目标或问题命名和组织；
- MUST 明确适用条件、前置状态和完成判据；
- MUST 聚焦行动、判断点和验证方法；
- SHOULD 处理真实环境中的主要分支、限制和失败恢复；
- SHOULD 假定读者已具备基础知识；
- MUST NOT 从工具按钮、内部模块或作者组织结构出发堆砌操作；
- MUST NOT 承担系统教学或完整接口参考职责。

典型标题：

- “如何配置网络自动重连”
- “如何定位固件烧录失败”
- “如何为新组件接入 Kconfig”

### 5.1.3 参考资料（Reference）

标准中文名：**参考资料**  
元数据值：`reference`

参考资料是面向查询的权威技术描述，其结构 SHOULD 对应产品、接口或硬件本身的结构。

参考资料：

- MUST 准确、客观、简洁且结构一致；
- MUST 标明适用产品、版本和限制；
- API 页面 MUST 与公开头文件、符号和错误码一致；
- 参数、返回值、单位、范围、默认值、并发约束和错误条件适用时 MUST 给出；
- 硬件参考 MUST 使用正式器件、引脚、电气和射频资料；
- MAY 提供短小示例帮助理解用法；
- MUST NOT 使用示例代替完整约束；
- MUST NOT 将推测、经验性意见或未经验证的能力写成产品事实。

典型标题：

- “GPIO API 参考”
- “构建目标与产物参考”
- “目标硬件引脚与电气特性”

### 5.1.4 解释说明（Explanation）

标准中文名：**解释说明**  
导航栏目 MAY 使用“架构”“概念”“设计说明”  
元数据值：`explanation`

解释说明面向理解，讨论概念、关系、背景、原因、约束和设计取舍。

解释说明：

- MUST 围绕一个边界清晰的主题；
- SHOULD 回答“为什么”“如何关联”“有哪些取舍”；
- SHOULD 连接架构、运行时行为、历史原因和现实约束；
- MAY 讨论替代方案和适用边界；
- MUST 区分事实、设计决策、推论和建议；
- MUST NOT 冒充逐步操作指南；
- MUST NOT 重复粘贴完整 API 定义。

典型标题：

- “启动流程与设计约束”
- “为什么应用层应优先使用 OSAL”
- “ROM 与 RAM 分离架构说明”

## 5.2 产品导航与一级目录职责

采用本规范的项目 SHOULD 使用以下一级结构；现有项目 MAY 在保持 URL 兼容的前提下逐步迁移：

```text
docs/zh-CN/
|-- FAQ/
|-- api-reference/
|-- get-started/
|-- guides/
|-- hardware/
|-- overall-architecture/
|-- samples/
`-- <index-page>
```

项目 MUST 保持一级入口职责清晰。每个一级目录 MUST 包含一个目录首页，并说明本目录服务的用户需求、内容范围和子栏目。首页的物理文件名和路由映射由采用项目决定。

纯路由目录首页 MUST 使用 `navigation` 类标识或等价的页面角色机制，MUST NOT 为满足内容类型校验而冒充 `tutorial`。导航与内容页的元数据边界见[第 6.1 节](06-authoring.md)。

| 一级入口 | 用户问题 | 主要类型 | 允许内容 | MUST NOT 成为 |
|---|---|---|---|---|
| 首页 | “我从哪里开始？” | 导航页，不属于四类内容 | 产品定位、支持范围、角色化入口、版本入口 | 技术细节和超长教程 |
| `get-started/` | “我如何成功完成第一次开发？” | 教程 | 环境准备、第一条 Happy Path、创建应用、烧录、首次验证 | 完整工具安装百科或命令参考 |
| `guides/` | “我如何完成某项真实开发任务？” | 实践指南 | SDK 开发、连接、网络、外设、安全、测试、认证、制造和排障任务 | 按内部模块堆砌的功能清单 |
| `samples/` | “我如何基于可运行案例完成具体开发任务或改造？” | 实践指南 | 与仓库源码一一对应的任务案例、角色、配置、预期输出、限制、改造边界、维护状态和测试证据 | 教程、API 清单，或无源码、不可构建、状态不明的占位页 |
| `api-reference/` | “接口的准确签名和约束是什么？” | 参考资料 | 驱动、中间件、OSAL 接口、错误码、数据结构 | 教学流程或长篇架构讨论 |
| `hardware/` | “硬件规格、设计和测试事实是什么？” | 参考资料 | 芯片、单板、器件选型、电气、射频和硬件测试资料 | 软件操作步骤的默认归宿 |
| `overall-architecture/` | “系统为什么这样设计、各部分如何协作？” | 解释说明；部分页面可为参考资料 | 软件分层、启动、运行时、内存、构建模型、目录边界 | CLI 操作手册或完整 API 清单 |
| `FAQ/` | “这个具体问题如何诊断和解决？” | 实践指南；少量参考资料 | 可搜索的问题标题、症状、原因、解决、验证和适用版本 | 未分类知识的收纳箱 |

1. `get-started/` MUST 围绕唯一首次成功目标和完成判据提供官方 Happy Path；入口、叶子教程及平台变体按[第 8.1 节](08-specialized-content.md)组织。环境详解 SHOULD 链接复用，但所选教程 MUST 直接提供或直接引导完成必要的最小准备。
2. `guides/` MUST 按用户任务或能力域组织；页面标题 SHOULD 使用动词或目标。
3. `samples/` 中除导航页外的案例页面 MUST 使用 `doc_type: how-to`，MUST 指向真实源码目录和 Kconfig 选项，并标明验证状态。学习型 Happy Path MUST 放入 `get-started/`，MUST NOT 以 Sample 页面代替教程。
4. `api-reference/` SHOULD 与源码模块结构对齐，但导航名称 MUST 对用户可理解。
5. `overall-architecture/` 中的命令操作 MUST 移至实践指南或参考资料；架构页 MAY 保留用于说明关系的最小命令片段。
6. `FAQ/` 现有大小写 MAY 为兼容 URL 暂时保留。新项目和完成重定向后的目录名 SHOULD 使用小写 `faq/`。
7. 新增一级目录 MUST 通过文档架构评审，证明现有目录无法表达其用户需求。

## 5.3 页面分类与归档决策

作者 MUST 使用以下问题确定 `doc_type`：

| 判断问题 | 是 | 文档类型 |
|---|---|---|
| 用户是否在受控路径中学习一项技能？ | 是 | `tutorial` |
| 用户是否已有目标，要完成任务或解决问题？ | 是 | `how-to` |
| 用户是否查询接口、参数、规格或确定事实？ | 是 | `reference` |
| 用户是否要理解原因、关系、背景或取舍？ | 是 | `explanation` |

如果页面对两个问题都回答“是”，作者 MUST 选择主要意图，并把另一部分拆出或链接到独立页面。

下列名称本身不足以确定文档类型：

- “用户指南”
- “开发指南”
- “说明”
- “手册”
- “示例”
- “FAQ”

作者 MUST 根据页面实际服务的用户需求分类，而不是根据历史文件名分类。
