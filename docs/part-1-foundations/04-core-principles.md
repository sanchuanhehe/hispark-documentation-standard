---
title: '4. 核心原则'
---

## 4.1 用户需求优先

文档 MUST 首先回答用户当前处于哪一种需求状态：

1. 学习一项技能；
2. 完成一个现实任务；
3. 查询准确事实；
4. 理解原因、关系与设计取舍。

栏目名称、代码模块或组织归属 MUST NOT 代替用户需求成为页面唯一的组织依据。

## 4.2 一个页面，一个主要意图

每篇内容页 MUST 声明一个且仅一个主要 `doc_type`。页面 MAY 链接到其他类型的文档，但 MUST NOT 为“内容完整”而把大段教学、操作、参考和解释混写在同一页面。

确有必要保留少量跨类型内容时，作者 MUST 保持主体意图不变，并链接到承担完整职责的页面。

:::{admonition} 背景与解决思路：页面职责混杂（非规范性）
:class: note

**问题背景。** SDK 文档在长期迭代中容易追求“一页讲全”，把环境准备、教学步骤、任务分支、参数表、原理和排障不断叠加在同一页面。新用户难以辨认成功路径，熟练用户也难以快速查询；各部分更新节奏不同，还会造成页面局部过时和 Review 范围持续扩大。

**解决机制。** 先确定页面服务的一个主要用户意图，再把其他需求拆到相应类型并建立链接，可以让读者预知页面提供哪类答案，也把更新责任和变更影响限制在更清晰的边界内。

**预期效果。** 教程更容易保持单一学习路径，参考资料更便于查询，原理说明和任务步骤不再相互遮挡；接口或流程变化时，团队能够更快定位需要更新和复核的页面。
:::

## 4.3 产品导航层与内容类型层分离

`get-started`、`guides`、`samples` 等一级目录是用户可见的产品导航层；Diátaxis 四类文档是页面内容类型层。二者 MUST 同时存在，MUST NOT 简单地把全部目录重命名为四个象限。

## 4.4 事实可追溯

与代码、接口、构建、硬件或版本有关的声明 MUST 能追溯到适用的源码、配置、发布物、测试或正式硬件资料。

文档 MUST 区分：

- 已由源码或配置静态核对；
- 已完成可复现构建；
- 已在目标硬件验证；
- 尚未验证或仅为示例。

静态检查 MUST NOT 被表述为已完成构建或 HIL（Hardware-in-the-Loop）验证。

## 4.5 产品与能力边界显式化

本规范 MUST NOT 预设任何具体芯片、产品、单板、协议能力或构建目标。采用项目 MUST 在页面元数据和正文中明确声明适用产品、版本、硬件对象、配置与验证范围。

1. 页面 MUST 只陈述其已声明适用范围内的事实和能力。
2. 页面 MUST NOT 因代码相似、产品同系列、上游支持或其他产品已验证，就推断当前产品具备相同能力。
3. 跨产品页面 MUST 枚举全部适用对象，并分别记录差异、限制和验证证据；无法证明共同适用时 MUST 拆分页面。
4. 未声明、未验证或仅由其他产品证明的能力 MUST 标记为未知或不适用，MUST NOT 进入默认推荐路径。
5. 示例中的占位产品、Target 和路径仅用于说明元数据结构，MUST NOT 被解释为本规范对具体产品能力的声明。

:::{admonition} 背景与解决思路：跨产品能力被错误带入（非规范性）
:class: note

**问题背景。** 多个产品可能共享 SDK 目录、相似接口或上游组件，作者复制相邻产品页面时又容易遗漏适用范围。用户看到内容位于某个产品站点，往往会把页面存在误解为该产品已经支持并验证了其中全部能力。

**解决机制。** 为每项能力声明明确适用产品、版本、硬件对象、配置和验证证据，并在无法证明共同适用时拆分页面，可以切断“代码相似即能力相同”的推断链。

**预期效果。** 导航位置不再被当作能力证据，Reviewer 可以逐项追溯各产品声明，用户也更不容易进入未经验证的组合。
:::

## 4.6 渐进迁移

现有稳定 URL SHOULD 保留。需要移动页面时，项目 MUST 提供重定向或兼容入口，并 MUST 修复站内引用。大规模目录调整 SHOULD 分阶段实施。
