## 9.1 领域验证

先看页面具体声称了什么，再选择能证明这项说法的检查。不同内容的最低验证方式如下。

| 内容 | 最低验证 |
|---|---|
| 纯概念与架构解释 | 技术评审，必要时源码静态核对 |
| 构建命令与 Target | 干净环境构建 |
| Sample 实践指南 | 对应配置构建；运行声明需要 Smoke/HIL；覆盖矩阵和证据必须更新 |
| API | 头文件或生成源比对 |
| 烧录、调试、连接流程 | 支持的工具与目标板验证 |
| 硬件规格 | 正式硬件资料评审 |
| 安全与不可逆操作 | 安全/领域 Owner 评审及风险说明 |

:::{admonition} 背景与解决思路：构建成功被误写为运行成功（非规范性）
:class: note

**问题背景。** 命令退出码为零、生成了产物，甚至触发了设备复位，都不等于示例已经运行成功。设备可能没有启动，连接可能没有建立，异常恢复也可能还没测。笼统地写“成功”，会让用户误以为这些都已验证。

**解决机制。** 逐项核对页面的说法，选择静态核对、构建、Smoke、HIL 或负向验证，并记录环境、观察到的标记和判断标准。这样才能看清每份证据证明了哪一步。

**预期效果。** 用户能分清“可以构建”和“已经运行验证”。Reviewer 能看出哪些说法证据不足，测试人员也知道还需要补测什么。
:::

## 9.2 Sample 测试覆盖模型

Sample 测试必须（MUST）分别记录以下覆盖维度，不得（MUST NOT）只写“测试通过”，却不说明哪些层级还没测：

| 覆盖维度 | 证明的问题 | 最低证据 |
|---|---|---|
| 映射覆盖 | 支持范围内的 Sample 是否都有文档、Owner 和测试入口 | Sample 清单及双向路径检查 |
| 静态覆盖 | 文档中的路径、符号、Kconfig、Target 是否存在 | 静态检查报告 |
| 构建覆盖 | 所需产品、Target、角色和配置是否能构建 | 命令、退出码、工具链版本和产物 |
| Smoke 覆盖 | 固件是否启动并出现最小成功标记 | 目标板、固件哈希和串口关键标记 |
| HIL 行为覆盖 | 文档声称的连接、传输、外设或协议行为是否成立 | 设备拓扑、步骤、日志、判据和结果 |
| 负向覆盖 | 错误输入、拒绝路径、超时、断连或恢复是否符合声明 | 触发条件、预期失败标记和恢复结果 |
| 版本覆盖 | 声称支持的 SDK、单板和工具版本是否经过验证 | 版本矩阵和最近运行记录 |

项目必须（MUST）维护 Sample 测试矩阵，至少包含：

- `sample_id`；
- 产品、SDK、Target、单板版本和工具链；
- 协议角色、对端、外设接线和前置资源；
- 必需配置及互斥配置；
- 静态、构建、Smoke、HIL 和负向场景状态；
- 成功与失败判据；
- 最近运行时间、执行环境和 Owner；
- 日志、产物、固件哈希或报告链接；
- 未覆盖原因、风险和补测计划。

覆盖率必须（MUST）使用明确分母计算，并必须（MUST）同时给出分子、分母、适用版本和统计日期：

```text
文档映射覆盖率 = 已建立有效文档映射的支持范围内 Sample 数 / 支持范围内 Sample 总数
构建覆盖率     = 构建通过的必需配置数 / 必需构建配置总数
HIL 覆盖率      = HIL 通过的必需场景数 / 必需 HIL 场景总数
负向覆盖率      = 通过的必需负向场景数 / 必需负向场景总数
```

仓库中的 Sample 数、文档页数或测试脚本数不得（MUST NOT）被表述为测试覆盖率。因硬件、权限或环境限制无法执行的场景必须（MUST）计入分母并标记为 `blocked` 或 `not_run`，不得（MUST NOT）计为通过。

:::{admonition} 背景与解决思路：覆盖率因分母缺失而虚高（非规范性）
:class: note

**问题背景。** 如果只统计已经接入自动化或跑过的场景，没接入的、因环境问题跑不了的，以及其他版本和角色组合，就都不算了。这样的覆盖率可能很高，却回答不了用户需要的场景是否测过。脚本数和 Sample 数也回答不了这个问题。

**解决机制。** 先列清支持哪些场景，再记录通过了多少、总共应测多少、适用版本和日期。`blocked`、`not_run` 的场景也列出来，才能看见还缺什么，以及后续怎么补测。

**预期效果。** 覆盖率能说明哪些对外承诺已经验证、用了什么证据，而不只是说明写了多少脚本。发布评审也能看到没测的部分及其风险。
:::

覆盖矩阵中的 `sample_id`、源码、文档、Owner 和状态必须（MUST）与[第 12.3 节](#sample-maintenance-contract) Sample 清单一致。

## 9.3 分层执行要求

| 阶段 | 必需（REQUIRED）检查 |
|---|---|
| Sample PR | 受影响页面严格构建、双向映射、受影响配置构建；涉及运行行为时执行对应 Smoke/HIL |
| 每日或定期任务 | 全量支持配置构建、代表性 Smoke/HIL、漂移和过期检查 |
| 发布候选 | 默认推荐 Sample 全量构建；所有对外行为声明对应的必需 HIL 场景；高风险负向和恢复场景 |
| 正式发布 | 覆盖矩阵、阻塞项、Known Issues 和证据归档完成 |

测试必须（MUST）采用失败关闭原则，即检查失败或证据不足时不放行。命令超时、设备无响应、串口静默、缺少关键成功标记、日志不完整或证据上传失败时，结果必须（MUST）为失败或阻塞，不得（MUST NOT）默认为通过。

测试报告必须（MUST）保留足以复现和审计的上下文，但不得（MUST NOT）泄露密钥、凭据、个人数据或受限信息。

## 9.4 Get Started 多变体验证矩阵

项目必须（MUST）为每个声明支持的“叶子教程、适用平台、交互方式”组合分配稳定场景标识，并分别记录下列阶段。合并执行时可以（MAY）复用证据，但必须（MUST）保留每个阶段的结论和适用范围，不得（MUST NOT）用一次 Build 通过代表整个教程通过。

| 阶段 | 检查边界 |
|---|---|
| source/static | 源文档、事实源、路径、元数据和渲染静态一致性 |
| environment | 所选路径的环境检查与必要准备 |
| configure | 配置命令、配置变化及最终生效配置 |
| build | 对应环境、版本和 Target 的构建及产物 |
| flash | 对应设备与工具的实际烧录结果 |
| serial | 串口访问、关键输出与判据；静默不算通过 |
| Smoke | 最小运行成功标记和关键路径 |
| HIL | 指定硬件拓扑上的端到端行为 |

每个阶段必须（MUST）使用下列状态之一，并记录判据、原因、证据及时间：

| 状态 | 含义 |
|---|---|
| `passed` | 已执行且证据满足该阶段判据 |
| `failed` | 已执行但判据未满足，或执行/证据完整性失败 |
| `blocked` | 因明确资源、权限或环境障碍无法完成 |
| `not_run` | 适用但尚未执行；不能隐含为通过或不适用 |
| `not_applicable` | 确实不适用于声明范围，并有可审查理由 |

必需阶段不得（MUST NOT）标为 `not_applicable` 来消除缺口；适用但未执行的阶段仍必须（MUST）计入覆盖分母。页面生命周期、证据等级与场景状态必须（MUST）分开处理，元数据规则见[第 6.1 节](../part-2-authoring/06-authoring.md)。

矩阵及其关联证据至少必须（MUST）包含：

- 叶子/变体/场景标识、页面和事实源版本、适用产品、Target、配置及硬件对象；
- OS 版本、Runner 类型与架构，SDK 和工具的精确版本或提交；
- 实际执行目录、命令、配置变化、退出码和完整日志；未执行项必须（MUST）显式为空并说明原因；
- 产物路径、字节大小和 SHA-256；阶段没有产物时必须（MUST）说明不适用，不得（MUST NOT）虚构产物；
- 开始/结束时间、成功判据、状态、验证边界和未覆盖范围；
- 阻塞或缺口的 Owner、补测计划及复核日期；镜像身份遵循[第 7.3 节](../part-2-authoring/07-upstream-downstream.md)。

Windows Server 上的非 HIL Build 只证明该 OS/Runner 环境内执行的构建。它不得（MUST NOT）被表述为 Windows 桌面、VS Code GUI、USB、烧录或 HIL 已验证。其他平台或交互方式之间的推断必须（MUST）受同样的证据边界约束。

## 9.5 可执行文档契约

文档与自动验证使用的版本、仓库、分支、Target、命令、配置变化和产物，必须（MUST）取自同一份机器可读事实源，或通过确定性检查证明等价。事实源必须（MUST）注明版本身份、Owner 和字段含义；不得（MUST NOT）把分别复制到文档和测试里的两套常量当作共享契约。

检查必须（MUST）覆盖从事实源到最终证据的各环节：事实源、生成器、源占位符、构建 Hook、渲染结果、Runner 和证据验证。未使用其中某层时，必须（MUST）记录不适用，并说明实际采用的替代流程。

检查必须（MUST）能发现占位符缺失或重复、构建集成没有执行、渲染结果过时或不等价、Runner 参数偏离事实源，以及产物或日志与声明不一致。成功判据必须（MUST）另有需求或正式资料作为依据，不得（MUST NOT）因为文档和测试使用了同一份错误数据，就认定结果正确。

工作流应当（SHOULD）只安排共享检查入口的执行顺序和条件，PR、Daily 与本地复用要求见[第 11 章](11-daily-ci.md)。为兼容旧调用而保留的包装代码，必须（MUST）登记调用方、Owner、移除条件和截止日期，不得（MUST NOT）无期限保留另一套实现。
