---
title: '11. 每日文档持续集成（Daily CI）'
---

每个采用本规范的项目必须（MUST）配置每日文档 CI，并应当（SHOULD）支持手动触发。Daily CI 必须（MUST）与 PR 门禁使用相同的锁定依赖和检查代码，不得（MUST NOT）另写一套无法在 PR 或本地复现的脚本。

:::{admonition} 背景与解决思路：没有文档提交也会发生漂移（非规范性）
:class: note

**问题背景。** 没有人修改文档，也不代表文档一直正确。外链和上游页面会移动，SDK、Target 和硬件环境会变化，Owner、例外和验证记录也可能失效或到期。这些变化不一定触发文档 PR 检查。如果定时任务没跑，却仍显示上次的绿色结果，就会掩盖当前问题。

**解决机制。** Daily CI 用与 PR 相同的检查代码，定期检查全部外部依赖、内容对应关系和有效期。没有执行、缺少证据或检查失败，都明确记为失败或阻塞。

**预期效果。** 即使仓库没有新提交，也能发现文档失效，并记录哪里出了问题、何时发现、依据是什么、由谁处理，避免把过期内容继续推荐或发布。
:::

Daily CI 至少必须（MUST）执行：

1. 全量严格站点构建、导航、内链、锚点、图片和大小写检查；
2. 全量上游 URL、目标锚点、固定版本可用性及版本漂移检查；
3. 下游与上游疑似重复内容扫描，并输出待人工确认清单；
4. `get-started/` 预算、唯一 Happy Path、必要术语和隐含前置条件检查；
5. API、配置、Target、Sample 源码和文档映射漂移检查；
6. Sample 清单、构建矩阵以及应在当日执行的 Smoke/HIL 场景；
7. `last_verified`、临时上游副本、例外、阻塞项和 Owner 的过期检查；
8. 结果、失败原因、适用提交、依赖版本和证据产物归档。

Daily CI 必须（MUST）记录时区、计划表达式、最长允许未成功运行时间、告警接收方和故障 Owner。默认最多允许连续 24 小时没有成功运行；因平台故障未执行或证据未上传，必须（MUST）标记为失败或阻塞，不得（MUST NOT）沿用上一次绿色结果。

Daily CI 不得（MUST NOT）替代 PR 门禁。Daily 发现回归时必须（MUST）自动创建或关联可跟踪项，至少包含失败范围、首次发现时间、最近成功提交、Owner 和证据链接；影响默认 Happy Path、公开 API 或推荐 Sample 时必须（MUST）阻止相关发布。

## 11.1 必需检查的失败传播

PR、Daily 和发布流水线用于汇总最终结果的程序（最终聚合器），必须（MUST）列出所有必需步骤及其报告/证据，并逐项核对是否属于当前提交和本次运行。不得（MUST NOT）只检查已经运行的任务，或凭某个任务成功就判定整体成功。报告各字段的含义和处理规则见[第 10.5—10.6 节](10-review-and-merge.md)。

任一必需检查出现 `failure`、`cancelled`、意外 `skipped`、超时、缺报告、缺证据或上传失败时，最终结果必须（MUST）为失败或阻塞。

判定某项检查不适用，必须（MUST）依据执行前已明确、可审查的适用条件，并保留理由；资源不足、未触发或尚未接入，不得（MUST NOT）算作不适用。聚合器本身未运行或没有结果时，不得（MUST NOT）允许部署。

转存日志、使用管道或增加包装层时，必须（MUST）保留实际命令的退出状态；不得（MUST NOT）因为后续保存日志、清理或生成摘要成功，就覆盖前面已经发生的失败。任务失败后，仍应当（SHOULD）执行清理和证据上传；如果这两项也失败，必须（MUST）在最终结论中保留。

长任务应当（SHOULD）显示进度或定期发送心跳，必须（MUST）定义超时和取消处理，并在超时或取消后清理其子进程树；不得（MUST NOT）留下仍在写入产物的子进程。平台返回的任务状态如何转换为场景状态，必须（MUST）明确记录；被取消或跳过的任务不得（MUST NOT）记为 `passed`。
