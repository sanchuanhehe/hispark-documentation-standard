## 10.1 Pull Request 必需信息

文档 PR MUST 说明：

- 用户问题和页面 `doc_type`；
- 适用产品、版本与 Target；
- 事实来源或源码路径；
- 已执行的验证及结果；
- 未验证事项和风险；
- URL、导航或兼容性影响；
- 变更风险等级、所需 Review 类型和 Reviewer；
- 关联 Issue、例外或后续跟踪项。

## 10.2 Review 要求

文档 Review MUST 验证内容是否适合合入和发布，MUST NOT 只检查措辞或格式。作者 MUST NOT 批准自己的变更，也 MUST NOT 成为唯一 Reviewer。最终批准至少 MUST 来自一名未直接编写该变更的合格 Reviewer。

### 10.2.1 Review 类型与职责

| Review 类型 | 必须检查的内容 | 合格 Reviewer |
|---|---|---|
| 文档 Review | 用户意图、Diátaxis 类型、目录职责、结构、术语、可读性、链接和生命周期 | 文档 Maintainer 或目录 Owner |
| 技术 Review | 产品事实、API、配置、Target、限制、版本、上游差异和源码对应关系 | 对应领域 Owner 或其明确授权人 |
| 验证 Review | 构建、Smoke、HIL、负向场景、判据、日志和覆盖矩阵是否支持页面声明 | 测试/CI Owner 或具备相应环境的验证人 |
| 安全 Review | 凭据、权限、不可逆操作、安全配置、数据与供应链风险 | 安全 Owner 或相应风险领域 Owner |
| 发布 Review | 文档版本、发布物、导航、URL、Known Issues、例外和阻塞项是否一致 | 发布 Owner |

Reviewer MUST 只批准自己有能力判断的范围。无法验证的部分 MUST 明确请求其他 Reviewer，MUST NOT 以“看起来合理”代替技术或验证结论。

### 10.2.2 必需 Reviewer 矩阵

| 变更类型 | 最低必需批准 |
|---|---|
| 仅修正错别字、标点或失效链接，不改变含义 | 1 名文档 Maintainer 或目录 Owner |
| 新页面、实质性重写、页面类型变化或跨目录移动 | 文档 Maintainer + 领域 Owner |
| `get-started/`、默认 Happy Path、首页或一级导航变化 | 文档 Maintainer + 领域 Owner；涉及运行路径时再加验证 Reviewer |
| API、Kconfig、Target、构建、烧录、硬件或产品能力声明变化 | 领域 Owner + 文档 Maintainer；存在运行声明时再加验证 Reviewer |
| Sample 新增、推荐状态变化或测试覆盖变化 | Sample/领域 Owner + 测试/CI Owner + 文档 Maintainer |
| 上游引用版本、下游差异、临时副本或去重例外变化 | 文档 Maintainer + 领域 Owner |
| 安全、凭据、权限、不可逆操作或高风险配置 | 安全/风险领域 Owner + 领域 Owner + 文档 Maintainer |
| 发布候选、版本切换、大规模迁移或长期例外 | 发布 Owner + 文档 Maintainer + 所有受影响领域 Owner |

同一人 MAY 承担多个角色，但高风险变更 MUST 至少有两名独立批准人。项目人力不足以满足最低独立性时，MUST 记录例外、风险、补偿性验证、批准人和到期日期；作者自批 MUST NOT 作为例外。

### 10.2.3 Review 判定规则

Reviewer 在批准前 MUST 确认：

1. PR 必需信息完整，事实来源、适用范围和未验证边界可审查；
2. 页面主要意图和目录归属正确，不以 Review 顺便接受明显的信息架构债务；
3. 下游没有重复维护上游通用内容，`upstream_refs` 的项目、版本和目标章节匹配；
4. `get-started/` 变更没有引入额外认知障碍，且仍符合 Happy Path 预算；
5. 技术声明与源码、配置、正式资料或发布物一致；
6. 验证级别与证据一致，静态检查没有被描述为构建、Smoke 或 HIL 通过；
7. 命令、危险动作、预期结果、失败恢复和版本边界足以让目标用户安全复现；
8. 图片和可视化内容确有必要、可访问、可维护，且未泄露敏感或受限信息；
9. 自动门禁通过，或每个失败都有经过批准且尚未过期的例外；
10. 评论中所有阻塞问题已经解决，非阻塞建议已明确接受、拒绝或转为可跟踪项。

存在以下任一情况时，Reviewer MUST 请求修改，MUST NOT 批准：事实无来源、适用版本不明、上游内容被无理由复制、默认 Happy Path 无法复现、验证证据与声明不匹配、无 Owner、危险操作无恢复说明、必需 CI 被跳过，或阻塞评论仍未解决。

### 10.2.4 Review 记录与有效性

Review 记录 MUST 能回答“谁在何时基于哪个提交审了什么范围”。PR 或评审系统至少 MUST 保留 Reviewer、角色、结论、提交 SHA、关键证据链接、阻塞意见及其处置。

批准后发生影响技术含义、用户路径、风险、验证结果、上游版本或覆盖范围的实质变更时，原批准 MUST 失效并重新请求相应 Review。纯合并冲突处理只有在不改变渲染内容和技术含义时 MAY 保留批准。

生成式或自动生成文档 MUST Review 其事实源、模板/生成器变更和可读渲染结果；“由工具生成” MUST NOT 免除 Review。紧急修复 MAY 缩短 Review 周期，但 MUST NOT 跳过最低批准和自动门禁。

项目 MUST 通过 `CODEOWNERS` 或等价机制自动请求必需 Reviewer，并 MUST 定义 Review 响应时限、升级路径和长期无人评审时的替补 Owner。响应时限只约束开始处理的时间，MUST NOT 被用来迫使 Reviewer 在证据不足时批准。

## 10.3 自动门禁

文档变更 MUST 运行与代码变更同等明确的文档门禁。最低门禁包括：

1. 源格式语法与格式检查；
2. 使用锁定依赖执行项目定义的严格站点构建；
3. 内部链接、锚点、图片和导航目标检查；
4. 外链定期检查；
5. 页面结构化元数据的必填字段与枚举校验；
6. 路径大小写和重复标题检查；
7. 术语和禁用写法检查；
8. 代码片段或命令的最小验证；
9. 与源码绑定的 API、Sample 和配置漂移检查；
10. Sample 清单、源码、实践指南和测试入口的双向映射检查；
11. 受影响 Sample 的构建/Smoke/HIL 门禁及覆盖矩阵更新检查；
12. `upstream_refs` 的项目、版本、URL 和锚点检查；
13. 下游与上游疑似大段重复内容检查；
14. `get-started/` 页面、步骤、前置条件、分支和目标完成时间预算检查；
15. 图片引用、替代文本、孤立资产、重复文件哈希、文件格式、尺寸和大小检查；
16. 可编辑图源与导出产物映射检查；具备 OCR 或图像安全扫描能力的项目 SHOULD 同时扫描疑似凭据、个人数据和受限信息。

仅修改 `docs/**` 的变更 MUST NOT 绕过文档门禁。

语义重复检查 MAY 先以报告或警告方式运行，但命中项 MUST 由文档 Maintainer 判定并记录处置结果。链接可访问不等于版本适配；上游引用的版本匹配 MUST 单独校验。

## 10.4 完成定义

一篇文档只有在满足以下条件后 MAY 标记为 `verified`：

- 主要用户意图和 `doc_type` 明确；
- 适用范围、版本和 Owner 明确；
- 页面结构符合对应模板；
- 术语和产品边界一致；
- 所有链接和资源有效；
- 上游引用版本匹配，且下游没有无批准的重复内容；
- `get-started/` 符合规模预算并通过目标用户路径验证；
- 声明的命令、接口和结果有对应证据；
- Sample 页面具有有效的源码映射、Owner、测试状态和覆盖矩阵记录；
- 严格站点构建通过；
- 必需的技术、文档和领域评审完成；
- Review 记录能够追溯到当前提交，且没有未解决的阻塞意见；
- 未验证边界已显式披露。
