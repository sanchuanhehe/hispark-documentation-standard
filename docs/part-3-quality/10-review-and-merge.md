## 10.1 Pull Request 必需信息

文档 PR 必须（MUST）说明：

- 用户问题和页面 `doc_type`；
- 适用产品、版本与 Target；
- 事实来源或源码路径；
- 已执行的验证及结果；
- 未验证事项和风险；
- URL、导航或兼容性影响；
- 变更风险等级、所需 Review 类型和 Reviewer；
- 关联 Issue、例外或后续跟踪项。

(review-requirements)=
## 10.2 Review 要求

文档 Review 必须（MUST）验证内容是否适合合入和发布，不得（MUST NOT）只检查措辞或格式。作者不得（MUST NOT）批准自己的变更，也不得（MUST NOT）成为唯一 Reviewer。最终批准至少必须（MUST）来自一名未直接编写该变更的合格 Reviewer。

### 10.2.1 Review 类型与职责

| Review 类型 | 必须检查的内容 | 合格 Reviewer |
|---|---|---|
| 文档 Review | 用户意图、Diátaxis 类型、目录职责、结构、术语、可读性、链接和生命周期 | 文档 Maintainer 或目录 Owner |
| 技术 Review | 产品事实、API、配置、Target、限制、版本、上游差异和源码对应关系 | 对应领域 Owner 或其明确授权人 |
| 验证 Review | 构建、Smoke、HIL、负向场景、判据、日志和覆盖矩阵是否支持页面声明 | 测试/CI Owner 或具备相应环境的验证人 |
| 安全 Review | 凭据、权限、不可逆操作、安全配置、数据与供应链风险 | 安全 Owner 或相应风险领域 Owner |
| 发布 Review | 文档版本、发布物、导航、URL、Known Issues、例外和阻塞项是否一致 | 发布 Owner |

Reviewer 必须（MUST）只批准自己有能力判断的范围。无法验证的部分必须（MUST）明确请求其他 Reviewer，不得（MUST NOT）以“看起来合理”代替技术或验证结论。

:::{admonition} 背景与解决思路：笼统的“已 Review”掩盖责任缺口（非规范性）
:class: note

**问题背景。** 一次文档变更可能同时包含信息架构、产品事实、运行证据、安全风险和发布一致性。熟悉措辞或参与过讨论的人未必有能力判断全部声明，而一个不注明范围的批准会把无人判断的部分一起包装成“已经审过”。

**解决机制。** 先按声明类型拆分审查范围，再把每一组交给具备判断能力的 Reviewer，并记录角色、提交和结论，可以让批准与实际判断能力对应。

**预期效果。** 团队能减少越权批准和责任空白；发生实质修改时，也能准确判断哪些审查仍然有效、哪些需要重新请求，而不是机械增加 Reviewer 数量。
:::

### 10.2.2 必需 Reviewer 矩阵

| 变更类型 | 最低必需批准 |
|---|---|
| 仅修正错别字、标点或失效链接，不改变含义 | 1 名文档 Maintainer 或目录 Owner |
| 新页面、实质性重写、页面类型变化或跨目录移动 | 文档 Maintainer + 领域 Owner |
| `get-started/`、默认 Happy Path、首页或一级导航变化 | 文档 Maintainer + 领域 Owner；涉及运行路径时再加验证 Reviewer |
| API、Kconfig、Target、构建、烧录、硬件或产品能力声明变化 | 领域 Owner + 文档 Maintainer；存在运行声明时再加验证 Reviewer |
| Sample 新增、推荐状态变化或测试覆盖变化 | Sample/领域 Owner + 测试/CI Owner + 文档 Maintainer |
| 上游引用版本、下游差异、临时副本或去重例外变化 | 文档 Maintainer + 领域 Owner |
| 安全、凭据、权限、不可逆操作或高风险配置 | 安全/风险领域 Owner + 领域 Owner + 文档 Maintainer |
| 发布候选、版本切换、大规模迁移或长期例外 | 发布 Owner + 文档 Maintainer + 所有受影响领域 Owner |

同一人可以（MAY）承担多个角色，但高风险变更必须（MUST）至少有两名独立批准人。项目人力不足以满足最低独立性时，必须（MUST）记录例外、风险、补偿性验证、批准人和到期日期；作者自批不得（MUST NOT）作为例外。

### 10.2.3 Review 判定规则

Reviewer 在批准前必须（MUST）按[第 14.1 节](../part-4-governance/14-conformance-checklist.md)完成本次变更的适用检查，核对用户路径、技术来源、上游差异、验证证据、图片和自动门禁。专项依据由该清单链接到规则定义处。

解释性内容如存在，Reviewer 必须（MUST）按第 2.2 节执行删除测试，并核对背景、成因、作用机制和预期效果。

所有阻塞问题必须（MUST）已解决，非阻塞建议必须（MUST）明确接受、拒绝或转为可跟踪项。

存在以下任一情况时，Reviewer 必须（MUST）请求修改，不得（MUST NOT）批准：事实无来源、适用版本不明、上游内容被无理由复制、默认 Happy Path 无法复现、验证证据与声明不匹配、无 Owner、危险操作无恢复说明、必需 CI 被跳过，或阻塞评论仍未解决。

### 10.2.4 Review 记录与有效性

Review 记录必须（MUST）能回答“谁在何时基于哪个提交审了什么范围”。PR 或评审系统至少必须（MUST）保留 Reviewer、角色、结论、提交 SHA、关键证据链接、阻塞意见及其处置。

批准后发生影响技术含义、用户路径、风险、验证结果、上游版本或覆盖范围的实质变更时，原批准必须（MUST）失效并重新请求相应 Review。纯合并冲突处理只有在不改变渲染内容和技术含义时可以（MAY）保留批准。

生成式或自动生成文档必须（MUST） Review 其事实源、模板/生成器变更和可读渲染结果；“由工具生成” 不得（MUST NOT）免除 Review。紧急修复可以（MAY）缩短 Review 周期，但不得（MUST NOT）跳过最低批准和自动门禁。

项目必须（MUST）通过 `CODEOWNERS` 或等价机制自动请求必需 Reviewer，并必须（MUST）定义 Review 响应时限、升级路径和长期无人评审时的替补 Owner。响应时限只约束开始处理的时间，不得（MUST NOT）被用来迫使 Reviewer 在证据不足时批准。

能改变公开文档内容或验证结论的契约、生成器、渲染适配器、Runner 和测试必须（MUST）与受影响页面受到等价的 Owner 路由和 Reviewer 约束。评审及门禁触发必须（MUST）覆盖这些文件，不得（MUST NOT）仅以文档目录是否变化判断是否需要文档 Review。

## 10.3 自动门禁

文档变更必须（MUST）运行与代码变更同等明确的文档门禁。最低门禁包括：

1. 源格式语法与格式检查；
2. 使用锁定依赖执行项目定义的严格站点构建；
3. 内部链接、锚点、图片和导航目标检查；
4. 外链定期检查；
5. 页面结构化元数据的必填字段与枚举校验；
6. 路径大小写和重复标题检查；
7. 术语和禁用写法检查；
8. 代码片段或命令的最小验证；
9. 与源码绑定的 API、Sample 和配置漂移检查；
10. Sample 清单、源码、实践指南和测试入口的双向映射检查；
11. 受影响 Sample 的构建/Smoke/HIL 门禁及覆盖矩阵更新检查；
12. `upstream_refs` 的项目、版本、URL 和锚点检查；
13. 下游与上游疑似大段重复内容检查；
14. `get-started/` 页面、步骤、前置条件、分支和目标完成时间预算检查；
15. 图片引用、替代文本、孤立资产、重复文件哈希、文件格式、尺寸和大小检查；
16. 可编辑图源与导出产物映射检查；具备 OCR 或图像安全扫描能力的项目应当（SHOULD）同时扫描疑似凭据、个人数据和受限信息。

仅修改 `docs/**` 的变更不得（MUST NOT）绕过文档门禁。

语义重复检查可以（MAY）先以报告或警告方式运行，但命中项必须（MUST）由文档 Maintainer 判定并记录处置结果。未经判定或仍成立的发现必须（MUST）按第 10.5 节计入总体门禁；检查器的警告级别不得（MUST NOT）自动豁免问题。链接可访问不等于版本适配；上游引用的版本匹配必须（MUST）单独校验。

## 10.4 完成定义

一篇文档只有在[第 14.1 节](../part-4-governance/14-conformance-checklist.md)中所有适用项均满足，并完成本章规定的独立 Review 后，才可以（MAY）标记为 `verified`。其中：

- 页面类型、模板、术语、适用范围、版本、Owner 和状态必须（MUST）满足[第 5 章](../part-2-authoring/05-information-architecture.md)和[第 6 章](../part-2-authoring/06-authoring.md)；
- 上游版本匹配、内容复用及专项要求必须（MUST）满足[第 7 章](../part-2-authoring/07-upstream-downstream.md)和[第 8 章](../part-2-authoring/08-specialized-content.md)；
- 命令、接口和行为声明必须（MUST）具有[第 9 章](../part-3-quality/09-validation-and-testing.md)要求的证据，Sample 必须（MUST）具有有效映射及覆盖矩阵，未验证边界必须（MUST）明示；
- 严格站点构建必须（MUST）通过，必需评审必须（MUST）对应当前提交，且必须（MUST）没有未解决的阻塞意见。

项目治理与发布检查由[第 14.2 节](../part-4-governance/14-conformance-checklist.md)组织，不要求每位作者重复提交整套项目材料；其中已适用的门禁、发布阻断和维护要求仍然有效。

## 10.5 历史基线与总体门禁

历史基线必须（MUST）只用于按稳定发现身份分类 `known`、`new`、`resolved`，不得（MUST NOT）豁免当前问题。`baseline_new=0` 仅说明没有新增债务，不得（MUST NOT）代表总体质量合格。只要存在当前发现（`known` 或 `new`），整体质量、规范符合性和正式部署门禁不得（MUST NOT）为绿色，除非正式批准的限期例外按[第 12.2 节](../part-4-governance/12-governance-and-maintenance.md)改变了具体发现的处理。

项目可以（MAY）设置单独命名的增量回归信号，但必须（MUST）在名称、摘要和部署依赖中与总体门禁区分，不得（MUST NOT）用该信号冒充总体门禁或解锁发布。修改基线、删除报告、调整阈值或将发现改为警告不得（MUST NOT）被当作问题已解决。经证据确认的误报可以（MAY）关闭，但必须（MUST）保留依据及审查记录。

例外必须（MUST）保留原始发现和分类，单独记录适用条款、批准范围及有效期；到期或不匹配当前范围时必须（MUST）自动恢复阻断。总体报告必须（MUST）明示带例外的结论，不得（MUST NOT）把获批处置写成无发现或无条件符合。

## 10.6 CI 报告契约

每项发现至少必须（MUST）包含稳定规则 ID、仓库相对路径、可定位的位置、消息和 `known/new/resolved` 分类；发现身份及基线比较方法必须（MUST）可重复。非文件型发现必须（MUST）使用明确的逻辑对象位置，不得（MUST NOT）用空路径或空位置隐藏对象。

每次检查必须（MUST）归档完整、不截断、可解析的机器报告。报告必须（MUST）声明格式版本、检查范围、提交、运行标识及完成状态，含全部发现；零发现也必须（MUST）生成有这些字段的有效报告。JSON、TSV 或 SARIF 可以（MAY）作为载体，项目必须（MUST）定义其字段映射，不得（MUST NOT）依赖某个 CI 平台才能解释结论。

摘要必须（MUST）按规则和分类给出计数、当前发现总数、例外处置和验证边界，并提供完整报告链接。使用平台 annotation 时，必须（MUST）为每类配置少量代表项的显示上限，并链接完整报告；显示上限不得（MUST NOT）截断机器报告或改变计数。没有 annotation 能力的平台可以（MAY）使用等价的短摘要。

报告缺失、空文件、无法解析、未声明完成、计数不一致或上传失败时必须（MUST）失败关闭。消费者必须（MUST）核对报告的提交、运行身份与预期检查集合，不得（MUST NOT）使用旧报告或把未产出报告解释为零发现。上传成功必须（MUST）有可核验的归档位置或回执。

## 10.7 可复现构建与部署产物

锁定构建必须（MUST）覆盖依赖的传递闭包，包括配置、继承配置、hooks、plugins、主题覆盖、模板、资产、脚本和外部资源。项目必须（MUST）记录各项来源、版本或内容摘要及获取方式，验证在声明的公开构建环境中可访问、可复现；不得（MUST NOT）依赖维护者工作机的隐含文件或权限。不能公开获取的受限依赖必须（MUST）使用经批准的合法供应方式并显式披露边界，不得（MUST NOT）将不可访问的构建声称为公开可复现。

公开部署必须（MUST）依赖完整总体门禁和所有适用发布检查，必须（MUST）部署同一提交对应的已验证站点产物，并核对产物身份/摘要。部署阶段重新生成的未经核验站点或其他提交的绿色结果不得（MUST NOT）代替该产物。失败传播遵循[第 11.1 节](11-daily-ci.md)。
